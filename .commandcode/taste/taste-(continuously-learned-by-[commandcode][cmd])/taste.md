# Taste (Continuously Learned by [CommandCode][cmd])
- Prefer being shown planned changes and expected version/outcome information *before* execution — "do not run, just update and then tell me which software gets which version." Confidence: 0.80
- Prefer language-ecosystem version managers (e.g., mise) over system package managers (e.g., apt) for developer tooling like Node.js. Confidence: 0.75
- Shell-rc dotfiles must include initialization for all version managers and CLI tools installed by playbooks (e.g., `mise activate zsh` in `.zshrc`). Tools should work immediately in the user's configured login shell without requiring manual fixes after provisioning. Confidence: 0.70
- Prefer upgrading CLI tools to their absolute latest version rather than staying on the LTS-bundled default. When a tool like npm itself notifies about a newer major version, upgrade to it — don't settle for "this is what ships with Node 22 LTS." Confidence: 0.80
- When applying a fix or upgrade to a managed machine, apply it both immediately (live, via SSH) and codify it in the automation playbook for future reproducibility. "Fix it now AND fix it forever" — never leave the playbook stale while patching the live system. Confidence: 0.85
- Prefers provisioning automation to be non-interactive and deterministic: disable Homebrew auto-update/cleanup/hints in automated runs, and skip (defer to a manual terminal session) any step that requires an interactive sudo prompt rather than trying to automate passwordless sudo. One sudo-requiring cask upgrade should not abort the whole bundle. Confidence: 0.7
- Prefers verifying automation fixes end-to-end before declaring done — syntax-check the playbook and actually run the fixed command (e.g., `brew bundle install`) to confirm it completes. Confidence: 0.6
- Works across machines over SSH with nested tmux (Mac tmux → SSH → Linux tmux → nvim) and expects configs to behave identically on the remote Linux boxes — fixes must be deployable there via the Ansible dotfiles role, and config code should not assume macOS-only commands (e.g., `pbpaste`) exist on Linux. Probes whether a fix holds through the full SSH/nested-tmux chain before accepting it. Confidence: 0.85
- All dotfiles/config writes must go to the dots repo directory (e.g., `/Users/devops/dots/.config/nvim`), never directly to the live path (`~/.config/nvim`); the live path is a symlink and must not be written to. Re-stated explicitly as a hard rule ("All writes go to /Users/devops/dots/.config/nvim only, never to ~/.config/nvim directly"). Confidence: 0.95
- When editing config files, prefers a disciplined workflow: read every file before editing it, do targeted edits instead of full rewrites when a file already partially has what's needed, and limit changes strictly to the files in scope (e.g., "Do not touch LSP configs, keymaps, options, or any file outside lua/plugins/ and lua/config/lazy.lua"). Re-stated in the migration spec. Confidence: 0.9
- For config migration tasks, prefers "write the config files only" — do not run the editor/tool (e.g., nvim), do not install anything; verification is done by re-reading files and checking references, not by launching the tool. Re-stated explicitly: "Do not run nvim, do not install anything, just write the config files." Confidence: 0.9
- Prefers nvim-cmp + lspkind over blink.cmp for a "more mature, visually polished" completion setup — explicitly initiated the migration with that rationale. Confidence: 0.8
- Judges editor/UI polish against a known-good reference (e.g., a friend's setup like "Elliot's") and expects pixel-faithful rendering: colored Nerd Font icons rather than text fallback glyphs, colored kind labels, visible window borders, and the exact configured colorscheme background (Catppuccin Mocha #1e1e2e). Diagnoses rendering failures in detail and supplies targeted fixes (explicit symbol_map, fields ordering). Confidence: 0.85
- Describes symptoms in casual, sometimes technically-wrong terms (e.g., "p to copy" when `p` is paste in Vim; "pyright on the right side for every keystroke") — expects the assistant to verify against the actual config/keymaps and explain what's expected vs. broken rather than take the description at face value. Confidence: 0.7
- Expects yanking in nvim (inside tmux inside Ghostty) to reach the macOS system clipboard via the OSC 52 chain, and treats silent copy failures as config bugs to root-cause (including LazyVim clobbering `clipboard`) rather than something to work around. Confidence: 0.8
- Dictates exact file contents and numbered step-by-step specs for config changes (full Lua blocks, explicit symbol_map entries, verification criteria, rules section) and expects faithful, verbatim implementation; deviations from the given spec (e.g., using import lines instead of an extras key) must be clearly flagged with justification rather than silently improvised. Confidence: 0.7
